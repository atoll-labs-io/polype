## Conventions

- **This repository is Polype itself.** The method lives in `method/` (rules `AGENTS.md`, `commands/po-*.md`, `agents/`, `skills/<name>/SKILL.md`, `templates/`, `hooks/`), tooling in `bin/`, tests in `tests/`, documentation in French in `docs/`.
- **`.claude/` and `.polype/` are installed copies of `method/` used to run the pipeline on this repository.** Never edit them; change `method/` instead.
- **Method files are written in English**, except `method/commands/po-help.md` (French cheat sheet). Commands and subagents start their body with a `Reads settings:` line listing, in backticks, every setting they read; each such setting must exist in `method/templates/agents-local.md`. Commands that must not write code do not get Write/Edit/Bash; subagents that judge do not get Write.
- **Commands refer to templates as `templates/<name>.md`** (installed under `.polype/templates/`) and to the gate as `po-gate`.
- **Tests are bash**: one file `tests/<story-slug>.test.sh` per story, defining `test_<name>` functions that use the helpers of `tests/lib.sh` (`contains` is exact and case-sensitive, `needs_tool`/`lacks_tool` check frontmatter tools, `require_file`, `fail` ends the test). An acceptance criterion's name is its test function's name. The functions of a story's criteria are its oracle: they go in `tests/<story-slug>.oracle.test.sh`, written by the planner, and the story's other tests in `tests/<story-slug>.test.sh`, which exists only when it holds at least one test (`tests/run.sh` fails a file with no `test_` function). Tests check the clauses that matter, quoting short exact phrases of the file under test.
- **No text from Killer SaaS** (ADR-0006). `tests/overlap.test.sh` fails when a line of `method/` shares 8+ consecutive words with it. `docs/parite-killer-saas.md` describes each mechanism in French: write the method in your own words from those descriptions, never from any Killer SaaS source.
- When a story implements lines of the parity matrix, it updates their status cell in `docs/parite-killer-saas.md` to `fait — <path>` (or `partiel — …`), touching only its own lines.
- Keep existing tests green; change an existing test only when the story changes the clause it checks, and say so.
- Commit messages in English, no co-author trailer.

## Direction (since 2026-11-12)

Read `docs/direction.md` before anything else: it says where Polype goes and what it no longer does. In short:

- **What Polype is**: an independent building block on the intelligence side of agent-driven development. It assumes no particular setup: any external agent (a chat front-end, a scheduler, or for example a local voice assistant acting as a butler) queries it and carries the person's answers back, through the contract of `docs/interface-agent.md`. Never write a specific user's setup into the method or its docs; a setup is only ever an example.
- **Current milestone**: M21 bis (s177 to s179, the owner's decisions D6 b and D7 b of 2026-11-14 on security findings), in `docs/stories.md`; M21 (the interface) shipped on 2026-11-14. M22 is framed once M21 bis has shipped. s153, s154 and s155 are postponed, in `docs/stories-reportees.md`.
- **Next thing to do**: D1 to D4, then D11 and D12, were answered on 2026-11-13 (ADR-0105 to ADR-0108, ADR-0115 to ADR-0117 are `accepted`; the driver automaton is a Rust binary named `po`, one per machine, prebuilt per platform and checksum-verified with a source build as fallback, holding everything M21 adds while the existing hooks stay in bash). M20 is built. M21 was reworked on 2026-11-13 for the Rust binary (s164 to s173, each approved by the owner). For M21: `/po-drive`, once the owner asks for it.
- **Do not**: open a method milestone that neither a defect seen on a product nor a written strategic decision of the owner pulls; add a prose rule to `method/` without removing as many words from the same file; write a test that looks for a phrase no script reads; fix a wording-only review finding through a story; settle a technical choice alone; file a security matter in the tracker.
- **Criteria and tests (owner, 2026-11-13)**: a plan sorts each acceptance criterion into one of three cases. A script already reads what the criterion fixes: its oracle test checks that. The rule can leave prose for a small local script: the story writes and tests it. The rule speaks to a model: no oracle test and no phrase test, the reviewer judges it by reading, and the plan lists it as a candidate for a `po-eval` control arm (#208).
- **Pending decisions** wait in the decision inbox (`Decision inbox`, `po inbox`). Ideas with no product pulling them are issues labelled `parked`.
