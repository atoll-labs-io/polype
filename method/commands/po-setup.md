# /po-setup

Reads settings: none

Every other Polype command starts by reading `AGENTS.local.md`. This one creates it.

**If `AGENTS.local.md` is already there, do not touch it.** Print its settings and end with: "AGENTS.local.md already exists — edit it directly, or remove it and run /po-setup again." Absence is the expected case: no other command writes this file except `/po-architect`, which fills only its « Conventions » section, and the installer never writes it.

`AGENTS.md` is generated by the installer; you do not write into it.

## Step 1 — Look before asking
Collect what the repository states on its own:
- the package manager, from the lockfile present;
- the scripts the project really defines (package manifest, Makefile, task runner) — candidates for `Install`, `Test`, `Typecheck`, `E2E`, `Build`, and `Dev`, the command that starts the development server;
- the default branch: `git symbolic-ref --short refs/remotes/origin/HEAD`, or the current branch when there is no remote;
- whether the repository has a base, as `/po-architect` defines it: a package manifest, or source files outside Polype's own files (`AGENTS*.md`, `CLAUDE.md`, `docs/`, `.claude/`, `.polype/`, `.gitignore`);
- the forge, read exactly as `/po-ship` reads it (`## The forge's review rule` of `method/commands/po-ship.md`): which forge it is, whether it could be read and, if not, why, and whether the repository is collaborative.

These become the suggested answers. A command you did not find in a file stays `—`.

## Step 2 — Five questions, one AskUserQuestion call each, plus the Platform, design, QA stage and Ship confirmation follow-ups and the catalogue offer
1. How stories land: `Merge mode` `pr` when the repository has a remote, `local` only for a repository without a remote (suggest one from `git remote`), and the `Target branch` (suggest the default branch).
2. Who approves plans: `Plan validation`, `autonomous` suggested, or `human`.
3. Where the project starts, `Entry mode`: `replace` (an internal replacement for a paid SaaS), `adapt` (a competing product with an angle of its own) or `new` (an idea built from nothing).
4. Who draws the screens, `Design source`: `internal` (an agent skill draws them in the repository), `external` (they come from a tool outside it) or not decided yet. Only the source is asked here.
5. The project commands, `Dev` included, with your suggestions from step 1.

Before the catalogue offer and question 5, make one separate AskUserQuestion call for `Platform`: what the project builds, one or more of `web`, `mobile`, `cli`, `api`, `lib`, `xr`, `robot`. Offer the likeliest ones as options and let the free answer name any of the seven; write the answer separated by commas.

Then `Ship confirmation`, from what step 1 read of the forge. Collaborative → no question: write `human (forge)`, and the setup's last message says which signal made the repository collaborative. Solo or unreadable → one separate AskUserQuestion call for `Ship confirmation`, stating what the forge showed or why it could not be read, with the answers `automatic (chosen)` (suggested) and `human (chosen)`. Tell the person they change it later by asking in conversation; no agent changes a `(chosen)` value on its own.

Once the `Design source` answer is known, make one separate AskUserQuestion call for its detail: the `Design skill` when the answer is `internal`, the `Design tool` when it is `external`; the other one stays `—`. When the source is not decided yet, skip this call: both stay `—`.

Once the `Dev` and `Platform` answers are known, make one separate AskUserQuestion call for `QA stage`: `screens` (/po-qa walks the screens a story touches), `surfaces` (/po-qa checks every story whose `Surface` is not `—`) or `—`. Suggest `screens` only when `Dev` is not `—`. When `Dev` is `—` and `Platform` names a platform without a screen — `cli`, `api`, `lib` or `robot` — ask anyway, offering `surfaces` or `—`; otherwise skip this call: `QA stage` stays `—`, since QA cannot start the application.

When step 1 found no base, offer the catalogue before question 5, in one AskUserQuestion: each profile of Polype's catalogue (`boilerplates/*/profile.md` in Polype's repository, when it is at hand) whose `- Platform:` line names one of the project's platforms, with its name and origin, plus the answer "no profile". A chosen profile's `## Commands` block becomes the suggestions of question 5, copied verbatim. No profile fits those platforms → say so and carry on without one. When the catalogue cannot be reached, say so and carry on without a profile. A repository that already has a base gets no offer.

Nothing else is asked beyond these five questions, the `Platform` follow-up, the `Ship confirmation` follow-up, that design follow-up, the `QA stage` follow-up and the catalogue offer; every other setting keeps the template's value, `Story track` and `Flow threshold` included, and so do the model defaults: `Model strong: opus`, `Model light: sonnet`, `Light up to: 2`.

A `Design source` left at `—` is not a choice: every design command stops on it and asks for the source again. Setup never fills it on the user's behalf.

## Step 3 — Write and commit
1. Copy `templates/agents-local.md` to `AGENTS.local.md` at the repository root and fill in the answers. Keep one setting per line and no trailing comment. Leave the conventions placeholder as it is, unless a profile was chosen: then the conventions section holds one line naming `boilerplates/<name>/profile.md` and its `Commit profiled`, the profile `/po-architect` starts from.
2. Make sure `.gitignore` lists the `Worktree root` folder and `.env*`; add what is missing.
3. Rerun the installer if it is available, so `AGENTS.md` includes the new settings; otherwise say that `AGENTS.md` will catch up at the next install.
4. Commit `AGENTS.local.md`, `.gitignore`, `AGENTS.md`, `.claude/` and `.polype/` together (those that exist) as `chore: set up polype`, on the branch `framing/setup`, landed as `## Landing the framing` below says. Setup lands with the `Merge mode` and `Target branch` it has just written and the effective `Ship confirmation` of the forge it has just read. Never commit a `CLAUDE.md`: Claude Code reads `AGENTS.md` only while none exists (ADR-0073). Worktrees are created from `Target branch`: until this landing is merged, they would have neither the rules, nor the templates, nor the gate.

Finish with: "Polype is set up. Write stories in docs/stories.md, then run /po-research <story>." When a profile was chosen, add that the person brings the boilerplate into the repository at its `Commit profiled` and commits it before running `/po-architect`. Close by listing the model defaults written — `Model strong: opus`, `Model light: sonnet`, `Light up to: 2` — and say they are changed in `AGENTS.local.md`.

## Landing the framing
Every framing command lands its commit this way: this one, `/po-brief`, `/po-prd`, `/po-stories`, `/po-stories-review`, `/po-architect` and `/po-design-system` (ADR-0080, ADR-0081). The command works from the repository root, which stays on `Target branch`: no switch, no checkout, no stash. It never commits to `Target branch` directly and never pushes it. Each command names its own `<slug>`, the `<paths>` it commits and its `<message>`.

**Remote check**, as in `/po-ship`. `Merge mode: pr` with no `origin` remote → stop: a repository without a remote uses `local`. `Merge mode: local` with a remote → stop with "`Merge mode: local` is only for a repository without a remote (ADR-0080); set it to `pr`."

**Base.**
- `pr`: `git fetch origin`. No `origin/framing/<slug>` (`git rev-parse --verify --quiet refs/remotes/origin/framing/<slug>` fails) → `<base>` is `origin/<Target branch>`.
- A framing branch already on the remote is proven merged or not, as step 3 of `/po-ship` proves a ship:
  - On GitHub, the forge `## The forge's review rule` of `method/commands/po-ship.md` recognises from `origin`, the proof is the pull request: `gh pr view framing/<slug> --json state --jq .state` prints exactly `MERGED`. Any other state, or no pull request from that branch, means not merged. `gh` missing or not logged in → stop: Ancestry is never the proof of a merge on GitHub, which rebuilds every commit it lands (ADR-0081).
  - On any other forge, where the merge is a true fast-forward (ADR-0081), the proof is `git merge-base --is-ancestor origin/framing/<slug> origin/<Target branch>`.
- Not merged → `<base>` is `origin/framing/<slug>`, whether a pull request is open or not. The new commit stacks on what the branch already carries, and an open pull request carries both.
- Merged → the root realigns before anything is built: in the root, `git merge --ff-only origin/<Target branch>`. A refusal is reported and the landing carries on: no stash, checkout or reset forces it. Then `git push origin --delete framing/<slug>`, and `<base>` is `origin/<Target branch>`. A merged branch is never taken as a base.
- That ref missing → stop: a person pushes `Target branch` to the remote once, since no agent pushes it.
- `local`: `<base>` is `framing/<slug>` when that local branch exists and is not an ancestor of `Target branch`; otherwise `<base>` is `<Target branch>`.

**The commit, built beside the checkout** (as the settings commit of `/po-ship`):
- Build a temporary index: `GIT_INDEX_FILE=<tmp> git read-tree <base>`, then `GIT_INDEX_FILE=<tmp> git add -- <paths>`.
- When `core.hooksPath` is `.polype/hooks`, run `GIT_INDEX_FILE=<tmp> .polype/hooks/po-gate.sh pre-commit`; a refusal stops the landing, since `commit-tree` runs no hook and this is the only secret scan the commit gets.
- `GIT_INDEX_FILE=<tmp> git write-tree` prints `<tree>`; `git commit-tree <tree> -p <base> -m "<message>"` prints `<sha>`. Remove the temporary index.
- Then `git add -- <paths>` in the root's own index: the root keeps these files uncommitted, and a later fast-forward of the root refuses untracked or modified copies of them unless they are staged.

**`Merge mode: pr`**
- `git push --force-with-lease=framing/<slug> origin <sha>:refs/heads/framing/<slug>`. A refused push is never forced: stop and report it.
- Reuse the pull request already open from `framing/<slug>`, or open one with `gh pr create --base <Target branch> --head framing/<slug>`, titled `<message>`. On a forge where no pull request is opened yet (ADR-0081: GitHub only), the branch is sent and the report asks a person to open the pull request.
- The effective `Ship confirmation` is the one `## The forge's review rule` of `method/commands/po-ship.md` settles; the line itself is never rewritten here.
- `human` → stop with "Framing pull request ready: <url>. Land it with Rebase and merge; /po-research starts a story only once its section is on `origin/<Target branch>`." Once a person merges, the next landing of any framing command realigns the root as **Base** says.
- `automatic` → when the pull request has checks, wait for them to pass; a failing check → stop and leave the pull request open. Then `gh pr merge <url> --rebase --match-head-commit <sha>`.
- Proof: `gh pr view <url> --json state --jq .state` prints exactly `MERGED`; anything else is not proof, and nothing below runs.
- Then `git fetch origin` and, in the root, `git merge --ff-only origin/<Target branch>`. A refusal is reported and the landing stands: never stash or check out to force it. Then `git push origin --delete framing/<slug>`.

**`Merge mode: local`**
- `git update-ref refs/heads/framing/<slug> <sha>`.
- `human` → AskUserQuestion "Land <message> on <Target branch>?", answers Merge / Not now. Not now leaves the branch in place, and the report says so.
- In the root, `git merge --ff-only framing/<slug>`, then `git branch -d framing/<slug>`. Nothing is pushed.

**Report.** The command's finish names the branch `framing/<slug>`, the pull request URL or the local landing, and the effective `Ship confirmation` with why: collaborative, solo, or unreadable with the call that failed.
