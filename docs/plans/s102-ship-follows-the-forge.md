   - **Which forge**, from `git remote get-url origin`: host `github.com` → GitHub; a host containing `gitlab` → GitLab; any other host → probe `https://<host>/api/v1/version`, and a JSON answer holding `version` → Forgejo/Gitea. No `origin`, no answer, or an unknown host → unreadable.
   - **How it is read**: through the forge's CLI when it is installed and logged in (`gh api`, `glab api`, `tea api` for Forgejo/Gitea — whether the installed `tea` has `api` is checked with `tea api --help`); otherwise `curl` on the API with the token the environment gives that CLI (`GH_TOKEN` or `GITHUB_TOKEN`, `GITLAB_TOKEN`, `GITEA_TOKEN`), sent in a header, never echoed, never written to a file. No CLI and no token → unreadable.
   - **The signals**, any one makes the repository **collaborative**:

## The pivot
**The effective value is decided at each ship from the forge, apart from the line; the line is a record that an agent rewrites only when it reads `(forge)`.** A collaborative repository gives `human` whatever the line, a `(chosen)` line included, but that line is not rewritten. This reconciles the owner's "the line becomes `human (forge)`" with `chosen_value_never_moves` and with the `(forge)`-only exception the criterion asks `method/AGENTS.md` to state; if the owner meant a `(chosen)` line to be rewritten too, task 3's rewrite rule and task 1's exception are where it changes. How it could be wrong:
- *The drive's waiting row reads only the line*: an `automatic` line on a collaborative repository then leaves an `OPEN` pull request every wave rerunning the whole ship, E2E included. Compare task 5's row (effective value) with task 3's effective-value rule.
- *A plan-limit 403 read as unreadable* would keep every free private repository on its setup value forever. Compare task 3's absence answers with the research probe.
- *The settings push written as a `git push` command line* turns `ship-through-pr` red, or worse, a push that names `Target branch`. Compare with ADR-0080 and `tests/ship-through-pr.test.sh:27-35`.
